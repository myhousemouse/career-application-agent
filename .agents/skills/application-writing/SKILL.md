# Application Writing Orchestrator

## 목적

기업 사실과 개인 경험을 각 원본 저장소에서 검증한 뒤 문항에 맞는 지원서 산출물로 결합한다. 이 저장소는 결합 결과만 보관하며 기업분석과 경험 원본의 복제본을 만들지 않는다.

## 1단계: 요청과 문항 확정

다음을 먼저 추출한다.

- 기업명, 법인명과 브랜드명
- 지원 직무·프로그램
- 공고 URL 또는 공고 원문
- 문항 원문, 글자 수와 마감일
- 사용자가 요구한 산출물: 소재 추천, 구조, 초안, 최종본, 면접 답변
- 사용자가 지정한 경험·말투·제외사항

정보가 일부 없어도 진행 가능한 분석은 먼저 수행한다. 결과를 크게 바꾸는 필수 정보만 사용자에게 묻고, 사실을 임의로 채우지 않는다.

## 2단계: 기업·직무 근거 확인

1. `/workspace/company_readme/README.md`와 해당 기업 디렉터리를 확인한다.
2. 분석이 없거나 공고 이후 중요한 변화가 있으면 `/workspace/company_readme/.agents/skills/company-analysis/SKILL.md`를 끝까지 읽고 기업·직무 분석을 수행한다.
3. 새 분석은 `/workspace/company_readme/<기업명>/`에 저장한다.
4. 지원동기에는 공식 미션·사업·직무 과제처럼 지원자가 실제로 선택한 이유와 연결되는 근거만 사용한다.
5. 회사 홍보문구를 나열하지 말고 `회사·직무의 특징 → 사용자가 관심을 가진 이유 → 경험에서 확인한 문제의식 → 기여 목표`로 연결한다.

## 3단계: 경험 근거 확인

1. `/workspace/experience/AGENTS.md`를 끝까지 읽는다.
2. 다음 인덱스와 AGENTS.md가 지정한 최신 정정 문서를 확인한다.
   - `/workspace/experience/README.md`
   - `/workspace/experience/00_Career-Ontology/README.md`
   - `/workspace/experience/00_Career-Ontology/프로젝트 메타 인덱스.md`
   - `/workspace/experience/00_Career-Ontology/경험 매핑 테이블.md`
   - `/workspace/experience/00_Career-Ontology/직무별 해석.md`
3. `/workspace/experience/자소서 정리.md`와 경험별 에피소드 문서의 `이미 활용한 문항`·`원문 위치`를 확인한다.
4. 과거 자소서 원문과 최신 지원서 업데이트에서 해당 경험이 사용된 회사, 직무, 문항, 강조 관점, 사용한 수치와 표현을 확인한다.
5. JD를 역량 단위로 분해하고 경험 후보를 고른다.
6. 선택한 경험의 최신 확인 절, 원문, 에피소드 문서를 직접 읽는다.
7. 다음을 분리해 기록한다.
   - 본인이 직접 한 기획·분석·구현·검증·보조·학습
   - 팀 전체 산출물과 수상
   - 실제 측정 성과
   - 목표, 추정, 제안, 예상 효과와 미완료 작업
8. 자료가 충돌하면 최신 사용자 정정을 우선하고 충돌 내용을 숨기지 않는다.

### 과거 활용 이력 확인 기준

초안을 쓰기 전에 선택한 경험별로 다음을 짧게 정리한다.

| 경험 | 과거 회사·직무 | 문항 | 당시 강조 관점 | 재사용 가능한 사실 | 수정·제외할 표현 |
|---|---|---|---|---|---|

- 과거 문장을 그대로 가져오기보다 새 문항과 JD에 맞춰 같은 사실의 관점을 다시 선택한다.
- 같은 지원서의 여러 문항에서 동일 사건을 반복하면 서로 다른 판단과 행동이 명확히 구분되는지 확인한다.
- 과거 자소서의 수치·역할·성과가 최신 정정과 다르면 최신 범위를 적용한다.
- 과거 지원 회사에 맞춘 지원동기와 입사 후 계획은 수행 경험으로 재사용하지 않는다.

## 4단계: 근거 매핑

초안 전에 `02_근거_매핑.md`를 만들고 과거 활용 이력과 다음 표를 작성한다.

| 문항 요구 | 기업·JD 근거 | 사용할 경험 | 개인 행동·판단 | 확인된 결과 | 금지 표현 | 원본 경로 |
|---|---|---|---|---|---|---|

경험은 많아도 문항 하나에는 중심 경험 하나와 필요한 보조 경험만 사용한다. 같은 사건을 서로 다른 프로젝트처럼 중복 계산하지 않는다.

## 5단계: 작성

경험 에피소드는 STAR를 기본 골격으로 전개한다.

### STAR 전개 원칙

- **S(Situation)**: 사건의 배경과 문제가 왜 중요했는지 간결하게 설명한다. 팀 규모·기간·제약은 확인된 내용만 쓴다.
- **T(Task)**: 팀의 목표와 구분되는 본인의 책임, 해결해야 했던 과제와 성공 기준을 밝힌다.
- **A(Action)**: 가장 큰 비중을 둔다. 무엇을 했는지만 나열하지 않고, 확인한 근거, 판단 기준, 검토한 대안, 선택 이유, 이해관계자 조율과 검증 방법을 쓴다.
- **R(Result)**: 확인된 결과를 수치와 범위에 맞게 쓰고, 측정하지 않은 효과는 만들지 않는다. 결과가 제한적이면 한계와 배운 점, 이후 달라진 업무 방식을 함께 쓴다.

STAR 표제를 본문에 기계적으로 노출할 필요는 없다. 지원동기나 입사 후 목표 문항에서도 경험을 설명하는 구간은 STAR 흐름을 사용하되, 기업·직무 연결을 억지로 Result에 넣지 않고 별도 문장으로 자연스럽게 잇는다.

문항에 맞춰 다음 순서 중 필요한 항목을 사용한다.

1. 관심을 갖게 된 구체적인 계기
2. 당시 문제와 본인이 세운 판단 기준
3. 대안을 비교하고 선택한 이유
4. 본인이 직접 수행한 행동
5. 결과와 검증 범위
6. 경험의 한계 또는 추가로 기르고 싶은 역량
7. 기업·직무에서 실행하고 싶은 구체적인 목표

행동 목록보다 판단 과정이 드러나게 쓴다. 분량이 제한되면 S와 T를 먼저 줄이고 A의 판단·실행과 R의 검증 범위를 보존한다. 직무 목표는 내부 정보를 아는 것처럼 단정하지 않고, 입사 후 확인할 데이터·가설·이해관계자·실행안·성과지표를 제시한다.

## 6단계: 사실 검증

초안과 원본을 문장별로 대조한다.

- 숫자에 기간·분모·집계 범위가 있는가?
- 본인 역할과 팀 성과가 구분됐는가?
- 제안·예상 효과를 실제 성과로 쓰지 않았는가?
- 기업 사실에 출처와 기준일이 있는가?
- 개인적인 계기나 감정을 자료 없이 새로 만들지 않았는가?
- 선택한 경험의 과거 자소서 활용 이력과 최신 정정을 확인했는가?
- STAR에서 본인의 과제와 행동이 구분되고, 행동의 판단 기준과 선택 이유가 드러나는가?
- 글자 수 제한을 지켰는가?

검증되지 않은 문장은 삭제하거나 확인 필요 표시를 한다. 그럴듯함을 위해 사실을 보충하지 않는다.

## 7단계: 윤문

사용자가 글 다듬기나 AI 티 제거를 명시했을 때만 `/workspace/experience/.agents/skills/humanize-korean/SKILL.md`를 적용한다. 내용과 사실 검증을 마친 뒤 마지막 단계에 수행하며, 스킬의 참조문서·변경률·출력 규칙을 지킨다.

## 산출물

`applications/<기업명>/<YYYY-MM-DD_직무명>/` 아래에 필요한 파일을 만든다.

- `01_요청과_공고.md`: 사용자 요청, 문항, 제한, 공고 원문·URL
- `02_근거_매핑.md`: 기업·JD·경험 근거와 금지 표현
- `03_초안.md`: 구조와 초안, 확인이 필요한 부분
- `04_최종본.md`: 검증 및 요청된 윤문까지 끝난 제출 후보

최종 응답에는 사용한 기업분석과 경험 원본 경로, 남은 사실 확인 사항, 저장한 파일 경로를 짧게 밝힌다.
